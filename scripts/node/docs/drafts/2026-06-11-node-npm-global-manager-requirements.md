# npm / Node 全局环境管理脚本需求大纲

日期：2026-06-11
状态：Draft
目标脚本：`scripts/node/npm-global-manager.sh`
运行环境：macOS 本地交互式终端
运行模式：统一以 `nvm` 管理 Node.js，以 `npm -g` 管理全局包

## 设计定位

- 这不是 `brew-app-manager.sh` 的拷贝版，而是参考它的交互模式、菜单结构、确认机制、扫描后执行、结果汇总这些设计思路。
- Homebrew 脚本管理的是 `brew` 自己的数据模型：`formula`、`cask`、`tap`、`brew services`、`brew cleanup`。
- 新脚本管理的是 `nvm + Node.js + npm global packages` 这一套环境，核心对象不同，所以扫描方式、卸载边界、来源管理都要重新设计。
- Node.js 本体不通过 Homebrew 安装；统一走 `nvm` 官方安装方式。
- 项目级依赖不在这个脚本范围内；脚本只管理全局包和 Node 全局运行环境。

## 与 Homebrew 脚本的对应关系

- `安装项目`：保留，但拆成单独安装和批量安装，而不是只支持固定清单批量安装。
- `卸载项目`：保留，但只有“全局包卸载”一条主线，不再区分 formula / cask。
- `更新与升级`：保留，扫描 `npm outdated -g` 后做选择性升级。
- `Tap 管理`：不保留，替换为 `源管理`。
- `环境与依赖`：保留，但对象从 `Xcode CLT / Homebrew` 改成 `nvm / Node / npm`。

## 来源管理结论

- npm 没有与 Homebrew `tap` 一一对应的机制。
- 本地确认结果：
  - 当前 `npm` 可用。
  - 当前 registry 为 `https://registry.npmjs.org/`。
  - `npm config` 暴露的是 `registry` 与可选的 `@scope:registry` 配置，而不是类似 `tap` 的独立仓库挂载模型。
- 因此新脚本不做 `Tap 管理`，改做 `源管理`，聚焦：
  - 当前 registry
  - 官方源 / 镜像源切换
  - 自定义 registry
  - `scope registry`
  - `.npmrc` 摘要

## 总体原则

- 先扫描，再展示，再确认，再执行。
- 尽量优先使用 `npm` / `nvm` 提供的确定性数据，避免做过度猜测。
- 结果页保留 Homebrew 脚本那种“摘要块”风格：计划数量、成功数量、失败数量、跳过数量、剩余状态。
- 能单独做的动作不要强绑到批量流程里。
- 不把“环境清理”混进“卸载包”里；它应当是单独入口。
- 脚本启动后，进入主菜单前，应先展示一块简短的 Node / npm 基本信息摘要。

## 启动页要求

- 脚本启动时先渲染“当前环境摘要”，再显示顶层菜单。
- 这块摘要不是完整诊断页，而是快速状态卡片，目标是让用户一眼知道自己当前在什么环境里操作。
- 返回顶层菜单时，可选择重新刷新这块摘要，避免用户切换 Node 版本后看到过期状态。

建议默认展示：

- `node` 路径
- `npm` 路径
- `node` 版本
- `npm` 版本
- `nvm` 是否已加载
- 当前使用的 Node 版本
- 默认 Node 版本
- `npm global prefix`
- `npm global root`
- 当前 registry
- 当前 Node 是否由 `nvm` 管理

展示原则：

- 缺失项不要中断脚本，应显示为 `<unavailable>`、`<not-loaded>` 或等价状态。
- 摘要控制在一屏内，避免一启动就刷出过长输出。
- 完整详情仍放在“环境与依赖 -> 环境总览”里。

```text
        │   ├── 展示孤儿软链接候选项 → 让用户逐条审阅
        │   ├── 用户确认后删除 → 执行清理动作
        │   └── 输出清理结果 → 展示删除数量和失败项
        └── 清理 nvm 旧版本残留 → 安全回收不再使用的 Node 版本
            ├── 扫描 ~/.nvm/versions/node → 枚举所有已安装版本目录
            ├── 展示已安装版本和目录体积 → 提供空间视角
            ├── 当前版本禁止清理 → 避免删掉正在运行的环境
            ├── default 版本禁止清理 → 避免删掉默认目标
            ├── 有 global package 的版本禁止清理 → 避免误删仍承载工具链的版本
            ├── 用户确认后执行 nvm uninstall → 统一通过 nvm 卸载
            └── 输出清理结果 → 汇总释放空间与剩余版本
```

## 已确认的关键约束

- Node.js 安装方式固定为 `nvm` 官方脚本，不走 Homebrew。
- `nvm` 的验证方式使用 `command -v nvm`，不使用 `which nvm`。
- “Tap 管理”正式替换为“源管理”。
- `nvm` 安装完成后，只保证当前脚本进程内可加载；必须提示用户新开终端或手动 `source` shell 配置。
- npm 全局包批量安装第一版默认只走串行；并行安装仅作为后续高级选项。
- 保护包默认不参与普通卸载，至少包括：`npm`、`corepack`。
- 所有删除、卸载、覆盖、修改默认版本、修改 registry 的动作，都必须遵循：
  - 先展示影响范围
  - 用户确认
  - 执行
  - 执行后验证
  - 输出结构化总结
- 所有只读展示功能不得修改环境。
- 所有清理功能默认只处理确定性路径；模糊残留只能列为候选项，由用户确认后删除。
- 新脚本应保留 `brew-app-manager.sh` 的交互哲学：
  - 启动先显示当前 Node / npm 环境摘要，再进入顶层菜单
  - 顶层菜单
  - 子菜单返回上一级
  - 重要操作先展示扫描结果
  - 危险动作必须二次确认
  - 执行后输出结构化总结
